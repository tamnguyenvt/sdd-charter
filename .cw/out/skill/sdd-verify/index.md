## How to talk to the user

Talk in full sentences: compress what is said, never the grammar it is said in.

- **The answer first** — then why, then what comes next. Never open by
  announcing what you are about to do, never close with a recap or an offer
  of more help.
- **A line per step** — no text between routine tool calls: one line when a
  step of the walk starts, one with what it showed. Speak in between only to
  warn, to clarify, or to ask.
- **Verbatim** — commands, paths, ids, code and errors are quoted exactly; an
  error by its shortest decisive line.
- **Every negation kept** — never drop a not, never, no, only or except to
  save a word: a lost negation costs more than any word saved.
- **A question carries its case** — each question, and each `nit` or `q`
  put to the user, says first what you were doing, then what you met there:
  the problem; then the fix you propose — where there are several ways on,
  the one you propose; only then what you ask.
- **One reading** — a sentence that could be read two ways is written again
  until it cannot.
- **As long as `manifest.md` says** — where its **Conversation** is short, the
  default, a gate says only what it asks of the user, with its case, and what
  changed is never listed: the user reads the code and asks. Where it is
  detailed, each step reports what it did and what it showed.

1. Run the full test suite and every static check the project defines —
   look in `package.json` scripts, the `Makefile`, the CI config: tests,
   type check, lint, dependency rules. Every one must pass, and a failure is
   never skipped. The one exception is a known failure the baseline of this
   walk recorded: a check that fails with none but the failures it recorded
   — each failing test's name, each error's line — does not fail this step,
   and they are reported as known, never as caused by the change. A known
   failure that no longer fails is reported as fixed. Any failure the
   baseline did not record is a failure like any other.
2. Test it by hand, as a user of the story would: run the command, call the
   endpoint, open the page. For a UI, start the server and drive it with a
   browser tool such as Playwright, and look at the result. Read what the
   program logged and printed during the run — its output and error
   streams, its log files, the browser console — and report it, or say that
   nothing was logged. An error or a warning raised on the story's path
   fails this step, quoted as it was printed.
3. Run `check` of [sdd-specs](../../script/sdd-specs/index.md) if anything in the spec folder changed.

Report what was run and what it showed, quoting the decisive output, and end
on one line that sums it up — what was run, what it showed — the evidence a
`Done` story keeps. No claim of "works" or "passes" without that evidence from
this turn. A failure of any step is reported, never fixed here: nothing is
changed, and the walk goes back to the change.
